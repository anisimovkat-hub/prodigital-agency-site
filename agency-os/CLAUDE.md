# Agency OS

Внутренняя операционная система рекламного агентства ProDigital (Катерина Анисимова):
дашборд руководителя, проекты/клиенты/сотрудники, задачи (единый раздел с видами
«День / Недели / Список» + канбан + личные),
KPI с авторасчётом, заметки. Заменяет связку Notion + Trello + таблицы. Пользователи — владелец
(админ, видит всё) и ~5 специалистов (видят только свои проекты).

**Продакшн на 2026-08-16:** прикладные миграции до 0032 применены, включая план/факт,
сохраняемый порядок канбана и
календарный срок хранения выполненных задач. Включены рекламные
функции 0016–0019; роли/RLS, инвайты, автоматическое удаление старых выполненных,
генерация повторяющихся задач и учёт времени работают. Production собирается из ветки
`claude/agency-ops-mvp-design-ykrrn0`. Страницы «Проекты», «Задачи», «Доска», «Неделя» и
дашборд работают на реальных данных. Детальная Meta-аналитика показывает реальные кампании,
группы и объявления; недоступный токену кабинет больше не останавливает синхронизацию остальных.
На production реклама и органический контент объединены в одном разделе «Аналитика»:
«Обзор · Контент · Реклама», автоматические выводы, Instagram-пилот и публичный
отчёт клиента. Старый `/ads` оставлен только как перенаправление для прежних закладок.
Meta-приложению `Ads Monitoring` добавлены Instagram API with Facebook Login и разрешения
`instagram_basic`, `instagram_manage_insights`, `pages_read_engagement`, `pages_show_list` и
`business_management`. Новый токен с доступом ко всем текущим и будущим business assets хранится
только в sensitive env Vercel для Production/Preview; реклама и органика используют одно приложение.
Основная Meta-статистика обновляется ежедневно Vercel Cron: защищённый endpoint повторно
загружает последние семь дней, чтобы учитывать запаздывающую атрибуцию. Пользовательские
сигналы рекламы показывают рост CPA от 20% только вместе со снижением числа заявок; падение
показов и технические уведомления о свежести на дашборд не выводятся.
Пять сотрудников ранее получили временные пароли;
пароли в Git не хранятся и при деплоях не перевыпускаются.

## Архитектурные решения

- **Server Actions вместо API-роутов** — вся запись в БД через `"use server"` + `useActionState`,
  ошибки валидации возвращаются полем `errors: Record<string,string[]>`.
- **Быстрое редактирование задачи**: `priority` и `assignee_id` меняются прямо в строках
  «День / Список» и на карточке канбана. Название открывает общий `TaskDrawer` для полного
  редактирования; создание доступно и в дневном, и в списочном представлении. Все быстрые
  изменения проходят через общую server action, RLS и повторную загрузку серверных данных.
- **RLS как единственный слой прав** (0002): SECURITY DEFINER функции `is_admin()`,
  `is_project_member(pid)`, `can_access_task(tid)`, `has_profile()` — без рекурсии политик.
  UI не фильтрует по ролям (кроме скрытия admin-блоков) — база сама отдаёт только доступное.
- **Регистрация только по инвайт-кодам**: триггер `on_auth_user_created` на `auth.users`
  валидирует `raw_user_meta_data->>'invite_code'`, создаёт профиль с ролью из кода.
  Пользователи без метаданных (созданные админом через SQL) пропускаются триггером.
- **Личные задачи** = `tasks.project_id IS NULL` + creator/assignee = auth.uid().
  Страница «Личное» имеет вкладки «Мои» (project null + assignee=me) и «Делегированные»
  (creator=me + assignee≠me). Делегирование = смена «Исполнителя» в задаче, не отдельный статус.
- **Иерархия работ**: клиент → проект → задача → подзадача (`parent_task_id`) → чеклист.
  «Направление работ» (`tasks.workstream`, свободная метка типа «Сайт»/«Таргет») группирует
  задачи внутри одного проекта, не плодя проекты. Подзадача наследует `project_id` и `workstream`
  родителя (иначе RLS не пустит). Сквозные связи (напр. «бот») — через описание/метку, не деревом.
  Для больших зонтичных проектов (например, Мос.ру) целевая модель — сделать направление
  первым классом внутри проекта: статус, ответственный, задачи и привязанные рекламные кампании,
  сохраняя один клиентский проект и один агрегированный отчёт. До отдельной миграции текущая
  строковая метка остаётся совместимой и не превращается в самостоятельный проект.
- **Повторяющиеся задачи** (0006): шаблоны в `recurring_tasks` (frequency = daily /
  every_other_day / weekly + weekdays[] + anchor_date для чётности). Функция
  `generate_recurring_tasks(target date)` идемпотентно создаёт задачи на дату (дедуп по
  `tasks.recurring_task_id` + due_date), ежедневный pg_cron `generate-recurring-tasks` в 03:00 UTC.
  Сгенерированные задачи — обычные `tasks`, поэтому попадают в «Сегодня»/«Неделя»/дашборд.
  Блог «Личный бренд» устроен как обычный проект (не личные задачи), чтобы иметь направления и метрики.
  Страница «Повторы» позволяет владельцу создавать шаблоны, менять расписание и ставить их на
  паузу; сотрудники видят только назначенные им шаблоны согласно RLS.
- **Личные Google Calendar владельца** подключаются через два закрытых read-only iCal URL,
  которые хранятся только как sensitive production env `GOOGLE_CALENDAR_ICAL_URL` и
  `GOOGLE_CALENDAR_SECONDARY_ICAL_URL`. Server-only слой параллельно загружает оба календаря
  с кэшем 5 минут, продолжает работу при временной ошибке одного источника, убирает дубли по
  нормализованному названию и минуте начала (даже если окончание слегка различается), корректно
  разворачивает RRULE/EXDATE/исключения и приводит события к единому рабочему
  часовому поясу Agency OS (`Europe/Moscow`), независимо от TZ календарного источника. События видит только роль
  `owner` в «Сегодня», «Неделе», «Личном» и блоке «Мой день»; они не копируются в `tasks`,
  не получают чекбокс выполнения и не меняют RLS. Обычные приёмы пищи (завтрак, обед, ужин,
  перекусы) отфильтровываются; бизнес-завтрак остаётся как встреча.
- **Фильтр аудитории задач** (`lib/task-audience-filter.ts`) общий для Дня, Недель и Списка:
  Все / Мои / Личные / Команда / конкретный сотрудник. Сначала база ограничивает доступ через RLS,
  затем представление фильтрует уже разрешённые строки. Владелец выбирает любого активного
  сотрудника, специалист — себя и исполнителей из уже доступных ему задач.
- **Дашборд-пульт**: секции «Мой день» (задачи текущего пользователя на сегодня+просрочка),
  «Загрузка команды» (по каждому сотруднику open/in_progress/today/overdue, метка «свободен»),
  «Просрочено без отчёта» (делегированные мной, дедлайн прошёл, статус ≠ done). Всё считается в
  server-компоненте из `tasks`/`profiles`; RLS отдаёт владельцу все задачи. Верхние сводные
  карточки являются ссылками: проекты → `/projects`, задачи на сегодня и просрочка → `/today`,
  активные клиенты → `/clients`.
- **Утренняя сводка** (`/brief`, расчёт в `lib/daily-brief.ts`) — read-only представление
  встреч, просрочки, задач на сегодня, срочного, трёх результатов дня и подсказок владельцу
  по делегированию. Использует уже доступные через RLS задачи и оба личных календаря; сама
  ничего не назначает и не записывает.
- **Делегирование** = смена «Исполнителя» в редакторе задачи, НЕ отдельный статус. «Личное»
  имеет вкладки «Мои» (project null + assignee=me) и «Делегированные» (creator=me, assignee≠me).
- **Редактирование клиента/проекта** — формы `client-edit-form`/`project-edit-form` (updateClient/
  updateProject) в `<details>` на страницах `[id]`; переименование и правка всех полей. Оба
  action возвращают фактически обновлённую строку, а формы показывают явное подтверждение.
- **Быстрые изменения проекта** — в таблице `/projects` цветные плашки «Статус» и «Стадия»
  являются нативными select-контролами и сохраняются сразу после выбора. Быстрая смена стадии
  использует ту же синхронизацию статуса клиента, что и полная форма. На странице проекта
  полная форма открывается заметной кнопкой с карандашом в строке названия.
- **Стадии и порядок проектов** — `launching` («На запуске») стоит выше активных, `paused`
  — после них, `finished` — в архиве. Единый `sortProjectsForDisplay` используется в списках
  и селекторах, чтобы приостановленные проекты не отвлекали от текущей работы. Стадия
  `launching` считается активной при расчёте статуса клиента и загрузки команды.
- **Пауза проекта останавливает операционную работу** — задачи проекта со стадией `paused` или
  `finished` не участвуют в «Доске», «Сегодня», «Неделе», активном списке задач, дашборде и
  загрузке сотрудников. При переходе проекта на паузу его незавершённые задачи переводятся в
  `paused`, открытые автоинтервалы времени закрываются существующим trigger, а шаблоны повторов
  выключаются. При реактивации задачи возвращаются в колонке «На паузе», но повторы нужно
  включить вручную, чтобы неожиданно не возобновить регулярную работу.
- **Доска имеет два явных режима порядка**. По умолчанию «По важности»: сначала задачи, где
  заполнены и дедлайн, и приоритет; затем только дедлайн, только приоритет и задачи без обоих
  признаков. Внутри групп учитываются просрочка/сегодня, уровень приоритета, флаги важности и
  ближайшая дата. Режим «Мой порядок» сохраняет drag-and-drop вверх/вниз и между колонками в
  `tasks.board_position` через атомарную SECURITY INVOKER RPC; RLS остаётся источником доступа.
  Выбранный режим запоминается в браузере. «На паузе» расположена перед «На проверке».
- **Отмена задачи — не удаление**: `tasks.status=cancelled` исключает задачу из активных
  представлений и закрывает автотаймер, но сохраняет запись и её историю. Используется, когда
  проект или запуск отменён; статус `done` остаётся только для реально выполненной работы.
- **Завершение проекта — архив, не удаление**: `projects.stage=finished` скрывает проект из
  текущей аналитики и переносит его в раскрываемый блок «Завершённые проекты». Клиент получает
  статус `active`, `paused` или `churned` из стадий всех своих проектов; при реактивации проекта
  автоматически возвращается в текущие клиенты и аналитику. Клиенты `churned` видны в отдельном
  архивном блоке и сохраняют всю историю.
- **Оценка задач хранится в минутах** (`estimate_minutes`), а формы принимают часы и округляют
  `часы × 60`. Форматирование длительности централизовано в `lib/format.ts`.
- **Автоматический учёт времени задач** хранит интервалы в `task_time_entries`: DB-триггер
  открывает интервал при статусе `in_progress` и закрывает при переходе в `review`, `paused`,
  `done` или любой другой статус. Возврат в работу открывает следующий интервал; галочка
  завершения использует тот же механизм. Несколько задач сотрудника могут идти параллельно:
  в недельной/месячной аналитике каждый пересекающийся отрезок делится между ними поровну,
  поэтому рабочий день не удваивается. Ручной проектный таймер `time_entries` сохранён отдельно.
- **Точный фокус пользователя** хранится отдельно в `focus_sessions`: у профиля одна
  `current_focus_task_id`, переключение выполняется RPC и атомарно закрывает предыдущий
  интервал. `task_status.ai_wait` означает ожидание ИИ и не считается человеческим временем;
  старый `task_time_entries` остаётся грубой оценкой состояния задач.
- **Единый редактор задачи** открывается в боковой панели из таблицы и канбана. Основные поля,
  описание, чеклист, комментарии и ссылки меняются через Server Actions; RLS остаётся
  единственным источником прав.
- **Изменения подтверждаются результатом БД**: Server Actions редактирования клиента, проекта
  и задачи возвращают обновлённую строку через `.select(...).maybeSingle()`. Пустой результат
  считается ошибкой доступа, а не успехом. После успеха формы пересобирают поля из возвращённой
  строки, чтобы исходные props не оставались на экране и повторное сохранение не откатывало данные.
  Инлайн-дедлайн читает значение из нативного `FormData`, а не из потенциально отставшего
  React-state. Дедлайн задачи можно быстро менять прямо в таблице «Задачи»; остальные поля
  остаются в общем боковом редакторе.
- **Цвет проекта вычисляется из project.id** (`lib/project-colors.ts`) и показывается через
  общий `ProjectBadge`. Цвет стабилен между страницами и не требует поля в БД.
- **Логотип проекта** разрешается централизованно через `lib/project-logos.ts`: явный
  `projects.logo_url` имеет приоритет, затем используется локальный подтверждённый бренд по UUID,
  иначе показываются цветные инициалы. Файлы и источники описаны в `docs/PROJECT_LOGOS.md`;
  внешние сайты не используются во время отображения.
- **Instagram sync не скрывает ошибки Meta**: discovery проверяет доступные права токена,
  независимо пробует Facebook Pages и owned/client assets Business Manager и возвращает
  безопасную диагностику без токена. Insights повторяют запрос с `metric_type=total_value`
  для соответствующих метрик, ошибки показываются по аккаунтам/метрикам, а
  `last_synced_at` меняется только после фактически успешной загрузки. Account insights идут
  двумя пакетами (дневные и total-value), а публикации и их insights — через field expansion
  одним запросом на аккаунт. Это укладывает агентский портфель в лимит Server Action и Meta API;
  fallback остаётся точечным. Очевидные несовпадающие имена (Озимо, личный бренд, M&M,
  Единорожки) сопоставляются явными alias, остальные аккаунты назначаются владельцем в UI.
- **Ошибки источников аналитики видны владельцу**: `/analytics` не подменяет отказ Supabase/RPC
  нулевыми карточками. При частичной недоступности таблицы, миграции или RPC сверху появляется
  предупреждение, а остальные доступные данные продолжают отображаться. При выборе проекта
  тяжёлые campaign-day/conversion/audience запросы ограничиваются его кампаниями.
- **Жизненный цикл выполненной задачи** строится по `completed_at`: после отметки задача сразу
  уходит из активного списка, три дня доступна во «Выполненных задачах», затем полностью
  удаляется ежедневной задачей `pg_cron`. Правило едино для агентских и личных задач и не зависит
  от дедлайна. Триггер БД синхронизирует `completed_at` со статусом даже при изменениях вне UI;
  незавершённые и отменённые задачи очистка не затрагивает.
- **PostgREST embed с хинтом**: `profiles!projects_responsible_id_fkey` обязателен —
  без него связь projects→profiles неоднозначна (вторая — через project_members) и запрос падает.
- **types.ts ведётся вручную** по миграциям (новая таблица → добавить в types.ts).
- **`src/proxy.ts`** — в Next 16 так называется middleware; matcher покрыт тестом proxy.test.ts.
- **Автодеплой из рабочей ветки** — Vercel подключён к GitHub: Production Branch =
  `claude/agency-ops-mvp-design-ykrrn0`, Root Directory = `agency-os`. Ручной fallback через
  Vercel MCP/CLI должен использовать тот же project/team ID. Production env хранится в
  настройках проекта Vercel, секреты и временные пароли в Git не попадают.
- **Маркетинговая аналитика разделена на ingestion и presentation**: реклама остаётся в
  `ad_*`, органика — в `social_accounts` / `social_account_metrics` / `social_posts`.
  `/analytics` объединяет их только при чтении и не складывает деньги разных валют. В UI
  это один раздел с тремя вкладками; отдельного пункта «Реклама» в навигации нет.
  Instagram использует server-only `META_ACCESS_TOKEN`; VK/Telegram позже добавляются
  адаптерами в те же social-таблицы.
- **Срезы аудитории Meta** (0021) хранятся суточно в `ad_audience_metrics` на уровне
  кампании: возраст, пол, страна, регион и площадка показов. `/analytics` агрегирует их
  по выбранным проекту и периоду; загрузка запускается отдельно, чтобы не замедлять
  основной sync рекламы. Вкладки «Обзор / Контент / Реклама» переключаются локально без
  повторного server-render и запросов к Supabase; аудитория показана внутри каждого среза.
  В Marketing API измерение передаётся только параметром `breakdowns`, а не дублируется в
  `fields`. Sync ограничивается кабинетами выбранного проекта, пишет строки параллельными
  пачками и сохраняет частично доступные срезы вместе с диагностикой недоступных. В рекламном
  экране расход, возраст, пол и страны образуют один компактный ряд; регионы и площадки
  остаются дополнительными раскрываемыми срезами.
- **Клиентский отчёт без логина не открывает внутренние таблицы**: секретный UUID ссылки
  проверяет SECURITY DEFINER RPC `client_report_payload`, который возвращает лишь агрегаты
  одного активного проекта. Прямого anon SELECT к CRM и рекламным таблицам нет.
