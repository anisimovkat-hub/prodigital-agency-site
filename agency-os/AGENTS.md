Когда владелец диктует/пишет задачу для сотрудника — следовать `docs/TASK_INTAKE.md`:
создать задачу в CRM (`tasks`) и выдать готовый текст в шаблоне владельца для пересылки

# Правила, выученные на сбоях (обязательны для Claude и Codex)

Записано 2026-10-26 после трёх проблем: обрыв синхронизации Яндекса, нередактируемые
статусы на странице клиента, медленная общая аналитика.

**Внешние API и cron**
- Объём работы на один кабинет должен быть ограничен и не зависеть от размера чужих
  каталогов. Нельзя запрашивать «все цели Метрики» (их бывает 800+): только видимые,
  основные, цели направлений и недавно сработавшие, не больше `YANDEX_SYNC_GOAL_LIMIT`.
- Любой cron укладывается в бюджет времени с запасом от `maxDuration`, обрабатывает
  кабинеты с ограниченной параллельностью, начиная с давно не обновлённых, и сохраняет
  результат каждого кабинета сразу. Пропущенные из-за времени кабинеты догружает
  отдельный catch-up запуск, а не следующий день.
- Перед изменением синхронизации посчитать в БД: сколько кабинетов, целей и строк она
  затронет в худшем случае. Обрыв по таймауту не пишет ошибку — его видно только по
  `last_sync_at`, поэтому после релиза проверять `last_sync_at` всех активных кабинетов.

**Тяжёлые страницы**
- Перед запросом «по всем проектам» оценить число строк (`count(*)` за период).
  `ad_conversions` хранит нули по каждой цели: общий обзор должен брать только строки
  с результатом (`count > 0`) и основные цели проектов, а не все десятки тысяч строк.
- Не передавать сотни UUID в `.in()` (огромный URL); не грузить данные, которые этот
  режим страницы не показывает (группы/объявления в портфельном обзоре).
- У каждого раздела с долгим серверным рендером есть `loading.tsx`, чтобы переход
  не выглядел зависанием.

**Единообразие интерфейса**
- Если владелец может менять поле в одном разделе, оно редактируется везде, где
  показано (общий компонент: `ProjectQuickSelect`, `ClientStatusSelect`), а не
  read-only плашкой. После изменения инвалидируются все страницы, где поле видно,
  включая динамические (`/clients/<id>`, `/employees/[id]`).

**Параллельная работа нескольких агентов**
- Каждый агент работает в своём worktree от свежего `origin` и коммитит только свои
  файлы. Перед push: `git fetch`, rebase/cherry-pick на свежий production, проверить,
  что `git log origin/<prod>..HEAD` содержит только свои коммиты, затем tsc, eslint,
  vitest, build. Никогда не `push --force` в production-ветку.
- Выкладывать по очереди: второй агент начинает деплой только после Vercel success
  первого и повторной синхронизации с `origin`.
