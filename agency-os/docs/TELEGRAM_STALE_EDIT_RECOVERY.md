# Старый режим правок перехватывал новые задачи

29.10.2026. Исправление подготовлено; миграция 0052 **не применена**, новая
версия ещё не выпущена. Реальные задачи, сообщения и настройки не менялись
во время подготовки.

## Подтверждённая причина

Read-only проверка рабочей базы показала один исторический черновик от сентября
со статусом `editing`, подтверждённой прежней доставкой и `expires_at=NULL`.
Его исходная задача была `paused`, с прежним высоким приоритетом.
Новые октябрьские сообщения попадали в редактирование этой задачи, меняли
название/проект/исполнителя/срок, но сохраняли paused и priority. Новых задач
не создавалось. После этого preview возвращал false до обращения к Telegram,
а приложение всё равно записывало `previewed=true` и завершало intake.
HTTP 200 означал ложное завершение; отсутствие ответа было реальным.

Приостановленную историческую задачу нельзя превращать в новую через todo
или смену проекта. Восстановление ранее перезаписанных полей — отдельная
операция владельца по проверенному исходному snapshot, этим кодом не выполняется.

## Подготовленный TS-фикс

- Нажатие «Внести правки» проверяет текущий статус задачи и её исходного проекта
  до включения editing. Остановленная работа не открывается для правок.
- При новом тексте старый editing проверяется до разбора правки. Если его задача
  закрыта/на паузе либо исходный проект неоперационный, отменяется только контекст
  черновика. Условный update проверяет id/task/review owner/status и возвращённую
  строку; конфликт не игнорируется. Cancel RPC, меняющий саму задачу, не вызывается.
- Связанный открытый intake правки закрывается по revision; текущий текст затем
  проходит обычное создание новой задачи без edit_draft_id. Старые complete-intakes
  и исходные задачи не переписываются.
- У правки, которая пережила уточнение/повтор доставки, актуальность исходной
  задачи повторно проверяется прямо перед commit RPC.
- RPC должен вернуть UUID; `sendTelegramTaskPreview` должен подтвердить true.
  При false нет `previewed`, перехода к следующей задаче или ложного complete.
  Уже записанный taskId сохраняется для повторного запроса без дубля.
- Операционные правки используют прежний RPC и общий preview. Утренний helper
  сохраняет штатный false/skip; cron, транспорт и расписание не меняются.

## Атомарная проверка SQL — отдельно на одобрение

Файл `supabase/migrations/0052_telegram_edit_operational_guard.sql` подготовлен,
но не применён. Он заменяет только существующий `commit_telegram_intake_item`.
В edit-ветке UPDATE проверяет **исходные** status/project_id задачи, а не новый
проект из текста: статус не done/cancelled/paused и исходный проект active/launching
(либо личная задача без проекта). Отказ не меняет строку и вызывает фиксированную
ошибку. Проверка затронутой строки обязательна. Существующие owner/profile/creator
проверки, создание todo/private задачи, idempotent taskId и ACL сохраняются.

Это закрывает окно между TS-проверкой и обновлением задачи. Сам TS-код не может
сделать две отдельные сетевые операции одной транзакцией. Никаких новых таблиц,
колонок, RPC, grants, расписаний или backfill миграция не содержит.

`scripts/check-telegram-stale-edit.sql` подготовлен и **ещё не выполнялся**.
Он создаёт только временные в транзакции fixtures и проверяет запрет paused/done/
cancelled, запрет правки todo из paused/finished исходного проекта даже при выборе
нового активного проекта, неизменность всей старой строки, активную правку,
обычное создание, idempotence и прежние права. В конце ROLLBACK. Реальные строки
используются только как FK-идентичности, без изменения; Telegram не вызывается.

До применения/SQL-проверки требуется отдельное одобрение владельца. Не выполнять
общий db push и не применять старые миграции повторно. После согласованного DDL
сверить и зарегистрировать именно 0052 в истории миграций.

## Проверка выпуска

Офлайн интеграционные тесты моделируют старый RPC, сохраняющий paused/high при
правке, чтобы воспроизвести прежнюю порчу: новое сообщение обязано создать
отдельный todo/private task, не изменив старую строку. Проверяются остановленные
задачи/проекты, условный конфликт, открытое уточнение старой правки, повтор
записанного edit-intake, активные правки и оба callback-сценария. При false preview
вторая задача не создаётся, повтор первой использует тот же taskId.

Локальные проверки: 573 теста / 62 файла, TypeScript, ESLint и production Webpack
build — PASS. Сборка использовала фиктивные публичные Supabase-параметры. SQL
rollback-сценарий не выполнялся; это не подтверждение применения 0052.

Живой тест выполняется после согласованных миграции и выпуска: владелец пишет
новое сообщение; в CRM должна появиться отдельная todo/private задача и личный
черновик. Историческая paused-задача не меняется. Отправка сотруднику — отдельное
явное действие владельца. Накопленные ложные complete-intakes автоматически
не переигрываются.
