# Ad Analytics — план полноценного модуля рекламной аналитики

Актуально: 2026-08-24. Meta + Instagram работают в production. Y1 Яндекс.Директа добавляет
owner-only read-only discovery через `AgencyClients.get`: без `Client-Login`, БД-записи,
исторической загрузки или изменения рекламы. Следующий шаг — проверить перечень, вручную
сопоставить кабинеты с активными проектами и только затем перейти к импорту. Подробная
реализация и критерии готовности: `docs/YANDEX_AI_ANALYTICS.md`. Исторический production audit
ниже сохранён как журнал и не отменяет текущий приоритет.

Вся аналитика использует одну кнопку периода в шапке `/analytics`: готовые интервалы слева,
два месяца календаря справа и «Обновить» для ручного диапазона. Она одновременно задаёт
показанный отчёт и обе read-only загрузки Meta (кампании и детали); отдельные поля даты и
быстрые select рядом с загрузками отсутствуют. Эти действия только догружают базу и не
меняют рекламу.

Без выбранного проекта `/analytics` — это не единый рекламный отчёт: экран по умолчанию
показывает недельные карточки отдельных активных проектов. Расход, CPL и цена цели считаются
строго внутри карточки; разные валюты и разные цели не объединяются. Общий график, KPI и
автовыводы доступны только после выбора конкретного проекта.

На 2026-08-20 заявка Яндекс.Директа для `ProDigital Agency OS — Яндекс.Директ (только чтение)`
была отправлена, а API отвечал кодом 58. На 2026-08-24 в личном аккаунте указан
«Программный доступ: открыт», но заявка от 20.08.2026 отклонена с комментарием «есть
совпадения по названию кампании». В заявке выбраны только JSON, агентский сценарий и
получение статистики/отчётов; управление рекламой не заявлено. Не повторять заявку и не
менять её условия наугад: 24.08.2026 запрос на конкретное разъяснение отправлен в чат
поддержки Яндекс.Директа, затем после ответа повторить
read-only `AgencyClients.get`.

Цель: превратить пилот (account-level статистика Meta) в полноценный аналитический
модуль внутри Agency OS: гибкие периоды, срез по проектам/кабинетам/кампаниям, разные
цели у разных кампаний, несколько пикселей, и верхняя панель «проблемные моменты».

Это большой модуль — вести поэтапно (Фазы A–D ниже), каждая фаза = рабочий, задеплоенный
инкремент.

## Требования владельца (цель модуля)

1. **Гибкие периоды**: выбор диапазона дат, гранулярность день/неделя/месяц.
2. **Срез по проекту**: выбрать один проект (или кабинет/кампанию) и смотреть только его.
3. **Разные цели у разных кампаний**: где-то лиды, где-то сообщения, покупки и т.д.
   В одном кабинете — несколько кампаний / продуктов / целей / пикселей.
4. **Верхняя панель «Требует внимания»**: аномалии и проблемные моменты
   (рост CPL/CPA, падение показов, ноль конверсий, слив/недокрут бюджета).
5. Позже: пересчёт валют в ₽ (кабинеты в USD/EUR/IDR/…); Яндекс.Директ тем же механизмом.

## Модель данных (расширение)

- `ad_campaigns` (id, ad_account_id FK, external_id, name, objective, status,
  project_id nullable, created_at, unique(ad_account_id, external_id)).
- Метрики на уровне кампании: расширить/дополнить `ad_metrics` полем `campaign_id`
  (nullable — account-level остаётся) ЛИБО отдельная `ad_campaign_metrics`. Хранить
  spend/impressions/clicks/reach по (campaign_id, date).
- **Конверсии по целям** (ключевое для «разные цели/пиксели»): гибкая таблица
  `ad_conversions` (id, campaign_id FK, date, action_type text, count numeric,
  value numeric, unique(campaign_id, date, action_type)). Сюда кладём ВСЕ action_type
  из Meta insights `actions` (lead, messaging, purchase, pixel-specific, и т.д.) —
  не схлопывая в один «leads». UI потом решает, какая цель «главная» для кампании/проекта.
- Опц.: `project_primary_goal` — какая цель считается основной для проекта (для CPL/CPA
  на дашборде). Можно поле на projects или на ad_campaigns.
- FX: `fx_rates` (currency, date, rate_to_rub) — для пересчёта в ₽ (Фаза D).

types.ts ведётся ВРУЧНУЮ — при каждой новой таблице/колонке дополнять.

## Загрузка (ingestion)

- Meta insights на уровне кампаний: `/act_<id>/insights?level=campaign&time_increment=1
  &fields=campaign_id,campaign_name,spend,impressions,clicks,actions,action_values
  &time_range={since,until}`. Пагинация по paging.next.
- Из `actions` писать КАЖДЫЙ action_type в `ad_conversions` (не только «lead»).
- Кампании upsert в `ad_campaigns` (наследуют project_id кабинета по умолчанию; можно
  переопределять вручную — у одного кабинета кампании могут относиться к разным продуктам).
- Идемпотентность через onConflict (как в пилоте).
- Историческая догрузка: параметризовать since/until (не только 30д).

## Фазы (поэтапно, каждая — деплой)

- **Фаза A — данные по кампаниям + конверсии по целям. СДЕЛАНО (см. раздел выше).**
  `ad_campaigns` + `ad_conversions`, ingestion на уровне кампаний, запись всех action_type.
  UI минимальный: таблица кампаний с расходом и разбивкой по целям за 30д.
- **Фаза B — аналитический UI. СДЕЛАНО (см. раздел выше).** Фильтры (период,
  гранулярность, проект/кабинет/кампания, цель) + графики временных рядов + таблица
  за период.
- **Фаза C — панель «Требует внимания». ОБНОВЛЕНО 2026-08-16.** Сравнение двух
  семидневных периодов: CPA вырос минимум на 20% **и одновременно** заявок стало меньше;
  отдельно сохраняются расход без результата и 14 дней без результата. Падение показов и
  техническая свежесть не показываются пользователю. Денежные сравнения выполняются внутри
  одной валюты и одинаковой цели.
- **Автоматическая загрузка Meta. СДЕЛАНО 2026-08-16.** Vercel Cron ежедневно в 03:00 UTC
  вызывает защищённый `GET /api/cron/meta-sync` и повторно загружает последние семь дней.
  Endpoint принимает только `Authorization: Bearer CRON_SECRET`, использует server-only
  `SUPABASE_SECRET_KEY`; оба значения хранятся как sensitive env Vercel.
- **Фаза D — валюты в ₽ + Яндекс.Директ.** `fx_rates` + пересчёт для сопоставимого CPA;
