# Ключевые решения (ADR)

## Принято

1. **Supabase + Vercel free-тиры** — владелец не хочет платить; масштаб (5 юзеров) укладывается.
   Компромисс: пауза БД после недели простоя; Hobby-план Vercel формально некоммерческий.
2. **Всё через Server Actions, без API-роутов** — меньше кода, типобезопасно, RLS работает
   через куки-сессию пользователя автоматически.
3. **Права только на уровне БД (RLS), не в UI** — невозможно «забыть» фильтр в новой странице;
   миграция 0002. SECURITY DEFINER хелперы, чтобы политики не рекурсировали
   (классическая ловушка profiles→profiles).
4. **Регистрация по одноразовым инвайт-кодам** (таблица invite_codes + триггер на auth.users),
   а не открытая регистрация — CRM с клиентскими данными; и не ручное создание — владелец
   просил самообслуживание. Роль зашита в код приглашения.
5. **Личные задачи = tasks.project_id IS NULL** — без отдельной таблицы; RLS показывает их
   только автору/исполнителю (и админу).
6. **Production-деплой из отдельной рабочей ветки** — Vercel подключён к GitHub:
   Production Branch = `claude/agency-ops-mvp-design-ykrrn0`, Root Directory = `agency-os`.
   `main` не используется для production. Ручной fallback через MCP/CLI допустим только с теми
   же project/team ID. Публичные `NEXT_PUBLIC_*` хранятся как production env проекта Vercel,
   а не в коммитах или одноразовом `.env.production` payload.
7. **Сотрудники заведены как auth-заглушки, затем получили временные пароли** (не инвайтами),
   потому что на их profile.id уже ссылаются projects.responsible_id. Пароли назначены 2026-07-19,
   email подтверждены; сами пароли в Git не хранятся.
8. **Демо-данные удалены, реальные july-проекты** — источник истины: скриншот владельца;
   Notion — только для поля «ответственный» (владелец предупредил, что Notion устарел).
9. **Названия ролей**: owner (админ/владелец), pm, specialist, viewer — enum user_role из 0001.
10. **Оценка задачи хранится в минутах** — поле `tasks.estimate_minutes`; формы принимают часы
    с шагом 0,25 и округляют `часы × 60`. Так суммы не зависят от ошибок floating point в БД.
11. **«Неделя» — текущая календарная неделя Пн–Вс** — просроченные и задачи без даты вынесены
    отдельно, внутри дней используется общий `sortTodayTasks`.
12. **Единый цвет приоритета** — классы левого акцента карточек находятся в
    `PRIORITY_ACCENT` (`lib/labels.ts`), а не дублируются в канбане.
13. **Настройки таблицы «Сегодня» локальны для браузера** — порядок столбцов меняется
    drag-and-drop и хранится в `localStorage`, потому что это личная настройка представления,
    не бизнес-данные. Сортировка выполняется клиентски по уже доступным через RLS задачам;
    исходный умный порядок сохраняется, пока пользователь не выбрал столбец.
14. **Один редактор задачи для списка и доски** — задача открывается в контекстной боковой
    панели без ухода со страницы. Поля сохраняются явной кнопкой, а чеклист, комментарии и
    ссылки — отдельными компактными Server Actions. Это сохраняет понятный контроль сохранения
    и переиспользует существующие таблицы без миграции.
15. **Цвет проекта детерминирован по UUID** — `ProjectBadge` строит читаемые HSL-цвета из
    `project.id`. Отдельное поле цвета и ручная настройка пока не нужны; один проект выглядит
    одинаково во всех представлениях, а название остаётся доступным текстом, не только цветом.
16. **Архив выполненных задач вычисляется по `completed_at`** — историческое решение,
    заменённое ADR 49. Отдельное поле архива не
    добавляется. Первые 30 дней задача доступна в разделе «Выполненные задачи», затем скрыта
    ещё 30 дней и удаляется после 60 дней ежедневным `pg_cron`. Это даёт окно для возврата
    ошибочно закрытой задачи и не хранит устаревшие рабочие данные бесконечно. Триггер
    `sync_task_completed_at` гарантирует корректную дату при любой смене статуса; RLS не менялся.

17. **Направление работ = поле `tasks.workstream`, а не отдельная сущность** — по выбору
    владельца. Один проект (напр. «Leaders First») содержит задачи с метками «Сайт»/«Таргет»;
    так не плодятся проекты, а группировка остаётся. Подзадачи — `parent_task_id` (наследуют
    project_id+workstream родителя). Сквозные связи (бот↔сайт↔таргет) — описанием/меткой, не деревом.
18. **Делегирование — это смена исполнителя, а не статус** — статусы заняты рабочим циклом
    (backlog…done). «Личное» разбито на «Мои»/«Делегированные» (creator=me & assignee≠me).
    Не вводили колонку «Делегировано» на доске, чтобы не смешивать «кто делает» и «на каком этапе».
19. **Повторяющиеся задачи — движок на pg_cron** (0006), а не внешний планировщик — уже есть
    инфраструктура pg_cron (0004). Шаблоны в `recurring_tasks`, `generate_recurring_tasks()`
    идемпотентна (дедуп по recurring_task_id+due_date). Сгенерированные задачи — обычные `tasks`,
    поэтому автоматически видны во всех представлениях. Владелец применил 0006 и сид вручную через
    SQL Editor (MCP Supabase был отключён) — двумя блоками (миграция + блог/шаблоны + generate).
20. **Блог/личный бренд — обычный проект «Личный бренд», а не личные задачи** — по выбору
    владельца: нужны направления (Контент/Постинг/Автоматизация) и попадание в дашборд/сегодня/неделю.
    Автопостинг каруселей нейросетью НЕ входит в CRM — это внешний пайплайн; CRM держит регулярную
    задачу + место под готовый файл + отметку «выложено».
21. **Дашборд-пульт считается в server-компоненте из уже доступных через RLS задач** — «Мой день»,
    «Загрузка команды», «Просрочено без отчёта» не требуют новых таблиц. «Просрочено без отчёта» =
    задача, делегированная мной (creator=me, assignee≠me), дедлайн прошёл, статус ≠ done.
22. **Один фильтр аудитории для «Сегодня» и «Недели»** — режимы Все / Мои / Личные / Команда /
    сотрудник используют общий чистый хелпер после выборки. RLS по-прежнему первым ограничивает
    доступные задачи; UI-фильтр отвечает только за представление и покрыт unit-тестами.
23. **Управление повторами — отдельная страница «Повторы»** — владелец создаёт и меняет шаблоны,
    сотрудники видят назначенные им шаблоны read-only. Это прямо повторяет RLS миграции 0006:
    `owner` управляет всеми строками, исполнитель читает свои. Остановка шаблона меняет
    `is_active`, не удаляет его и не затрагивает уже созданные обычные задачи.
24. **Изменение записи подтверждается возвращённой строкой, а не только отсутствием ошибки** —
    PostgREST при RLS-фильтрации может вернуть успешный ответ без изменённых строк. Поэтому
    критичные update-action используют `.select(...).maybeSingle()`: пустой результат
    показывается как ошибка прав/сессии. Проект и общий редактор задачи дают видимый success
    feedback. Для частой правки дедлайна выбран компактный инлайн-редактор в таблице; остальные
    поля редактируются в общей боковой панели, чтобы не превращать каждую строку в большую форму.
25. **Личный Google Calendar — отдельный read-only слой, а не импорт в `tasks`** — календарные
    встречи, спорт и поездки не являются задачами с чекбоксом и не должны дублироваться при
    каждом обновлении. Обычные приёмы пищи отфильтровываются до UI; бизнес-завтрак считается
    встречей. Закрытый iCal URL хранится как sensitive env Vercel и используется только
    server-only кодом; UI доступен лишь роли `owner`. `node-ical` разворачивает повторы,
    EXDATE и RECURRENCE-ID. Исходный TZ нужен для разбора абсолютного времени, но дневная
    группировка и отображение выполняются в едином рабочем TZ `Europe/Moscow`, чтобы календарь
    с прежней настройкой `Asia/Bangkok` не сдвигал события в интерфейсе. Компромисс iCal:
    редактирование остаётся в Google Calendar, обновление в Agency OS может отставать до 5 минут.
26. **Несколько личных календарей объединяются server-side, а не синхронизируются между собой** —
    каждый аккаунт даёт отдельный закрытый iCal URL в sensitive env Vercel. Источники загружаются
    независимо, поэтому сбой одного не скрывает другой; одинаковые события убираются по
    нормализованному названию, началу и окончанию. Оба источника приводятся к рабочему часовому
    поясу `Europe/Moscow` для общей дневной/недельной ленты. Это не требует OAuth-записи,
    миграции БД или изменения RLS.
27. **Автотаймер задач реализован DB-триггером и интервалами, а не клиентским секундомером** —
    `task_time_entries` открывается при `tasks.status = in_progress` и закрывается при выходе
    из него. Поэтому учёт одинаково работает при drag-and-drop, сохранении формы, галочке и
    будущих способах изменения статуса, даже если браузер закрыт. Параллельные интервалы
    сохраняются как есть для аудита, но аналитика делит каждый общий отрезок между задачами
    одного исполнителя: это соответствует работе через несколько нейросетей и не завышает
    рабочий день. Ручной таймер `time_entries` оставлен отдельным и не складывается с автотаймером.
28. **После записи форма синхронизируется с возвращённой строкой БД, а не с исходными props** —
    успешный action возвращает все редактируемые поля; uncontrolled-поля пересобираются с новым
    `key`. Иначе БД уже хранит новое значение, но форма показывает старое и повторным submit
    незаметно откатывает изменение. Для нативного поля даты submit читает `FormData` формы:
    это надёжнее отдельного React-state при работе браузерного date picker. Правило применяется
    одинаково к редакторам клиента, проекта и задачи.
29. **Единый дашборд не означает единую плоскую таблицу** — реклама остаётся в `ad_*`,
    органика в `social_*`; экран объединяет их при чтении. Так разные API и смысл метрик
    не смешиваются, а VK/Telegram можно добавить адаптерами.
30. **Клиентская ссылка работает через агрегирующий SECURITY DEFINER RPC** — anon не получает
    SELECT к CRM, рекламным или social-таблицам. UUID проверяется в `client_reports`, отчёт
    ограничен одним проектом и может быть отключён. Service-role в Next.js не требуется.
31. **Гибридный формат отчёта: обзор + два углубления** — «Вся система» отвечает клиенту,
    что происходит и что делать дальше; «Органика» подходит контентным проектам, «Реклама» —
    проектам с большим трафиком. Выводы только из реальных данных. Деньги разных валют не
    складываются: без одной валюты CPA/ROAS скрываются.
32. **Вкладки аналитики — presentation-state, фильтры — server-state** — переключение
    «Обзор / Контент / Реклама» не меняет набор данных и поэтому выполняется
    локально без новой навигации. Период, проект и аккаунт остаются GET-фильтрами и вызывают
    server-render. Срезы аудитории Meta хранятся суточно в отдельной admin-only таблице
    `ad_audience_metrics`; на экран не подставляются демо-значения, а при отсутствии sync
    показывается честное пустое состояние.
33. **Цели рекламы показываются по кампаниям, а не одной суммой на проект** — для каждой
    кампании выбирается её основная конверсия; если конверсии нет, используется измеримый
    traffic-результат (landing page view / link click / Instagram profile visit). Органический
    прирост подписчиков Instagram показывается отдельно и не приписывается рекламе без
    соответствующей метрики Marketing API.
34. **Логотип проекта имеет два уровня источника** — заполненный `projects.logo_url` имеет
    приоритет, а для подтверждённых брендов используется локальный файл, сопоставленный по UUID
    проекта. Внешний hotlinking не используется: логотипы не пропадают при сбое чужого сайта и
    не замедляют интерфейс. Неоднозначные названия получают прежнюю стабильную цветную заглушку,
    чтобы случайно не показывать бренд другой компании.
35. **Один пользовательский раздел аналитики, но раздельные источники данных** — отдельный
    пункт «Реклама» создавал дублирование фильтров и непонятную границу с «Аналитикой», поэтому
    в навигации остаётся один `/analytics`: «Обзор · Контент · Реклама».
    Детальные рекламные инструменты перенесены в контекст вкладки «Реклама», синхронизация
    Instagram — в «Контент». Старый `/ads` перенаправляет с
    сохранением фильтров. Это объединение presentation-слоя: `ad_*` и `social_*` не смешиваются,
    RLS и ingestion остаются прежними.
36. **Аудитория — сквозной блок, а не отдельный раздел** — возраст, пол, география и площадки
    помогают интерпретировать общий результат, контент и рекламу, поэтому один и тот же честный
    блок Meta показывается внутри всех трёх вкладок. Навигация остаётся из трёх заметных цветных
    карточек с иконками; «Обзор» открыт по умолчанию, старый `section=audience` ведёт на него.
37. **Завершение проекта — обратимый архив** — `stage=finished` не удаляет проект и его историю,
    но исключает его из текущей аналитики и основных списков. Клиентский статус выводится из
    всех связанных проектов: `active` имеет приоритет над `paused`, а только завершённые проекты
    дают `churned` (в UI «Завершён»). При реактивации проект и клиент автоматически возвращаются;
    клиент с другим активным проектом не архивируется.
38. **Ускоренная очистка ограничена личными done-задачами с дедлайном** — историческое решение,
    заменённое ADR 49. Через два календарных
    дня после `due_date` задача удаляется pg_cron, потому что в «Личном» важна короткая рабочая
    очередь, а не история выполнения. Незавершённые задачи сохраняются даже с очень старым
    дедлайном; done-задачи без даты остаются под общим 60-дневным правилом. В UI открытые задачи
    всегда выше выполненных и сортируются по возрастанию дедлайна.
39. **Состояние проекта меняется непосредственно из списка** — `health` и `stage` отображаются
    не декоративными badge, а компактными нативными select-плашками с автосохранением через
    отдельный Server Action. Action повторно проверяет авторизацию и enum-значения; изменение
    `stage` обязательно синхронизирует агрегированный статус клиента. Полная форма остаётся для
    остальных полей и открывается явной кнопкой в шапке проекта, а не нативным `<summary>`.
40. **«На запуске» — стадия проекта, а не поле режима ведения; отмена — отдельный статус
    задачи** — запуск требует операционного внимания и должен участвовать в текущей нагрузке,
    поэтому `project_stage.launching` сортируется перед `active`. `paused` опускается вниз, но
    не скрывается и остаётся легко реактивируемым. Для незапущенного проекта задачи получают
    `task_status.cancelled`, а не `done`: так отчёты не засчитывают отменённую работу как
    выполненную, при этом сохранены связи, комментарии и учёт уже затраченного времени.
41. **Пустая аналитика не считается успешной синхронизацией** — Meta discovery и insights
    возвращают структурированную диагностику вместо пустых массивов без объяснения. Ошибки
    одного аккаунта/метрики не отменяют остальные, но перечисляются владельцу; `last_synced_at`
    фиксирует только реально выполненный sync. Supabase/RPC ошибки отображаются отдельным
    предупреждением и не маскируются нулевыми KPI. Параллелизм Instagram ограничен небольшими
    пачками как защита от rate limit; секретный токен никогда не попадает в UI или логи.
42. **В рабочей аналитике только launching/active** — проекты на паузе и завершённые не входят
    в фильтр `/analytics`, чтобы не смешивать текущую работу и архив. История, данные рекламы и
    клиентские отчёты не удаляются; после возврата стадии в `launching` или `active` проект снова
    автоматически появляется в аналитике.
43. **Главные срезы аудитории живут рядом с динамикой, а sync ограничен проектом** — расход,
    возраст, пол и страны должны читаться на одном экране, поэтому они занимают четыре равные
    компактные карточки. Регионы и площадки остаются деталями по требованию. Обновление
    `ad_audience_metrics` получает `project_id`, выбирает только связанные кабинеты и пишет
    результат параллельными пачками; частичная ошибка Meta не отменяет доступные breakdowns.
    Параметр измерения передаётся только через `breakdowns`, иначе Graph API отклоняет запрос.
44. **Реклама и органика используют одно Meta-приложение, но синхронизируются пакетно** —
    `Ads Monitoring` уже имеет доступ к business assets, поэтому отдельное приложение увеличило
    бы число токенов и точек отказа без продуктовой пользы. Один server-only токен получает
    рекламные и Instagram permissions и хранится только в Vercel. Account insights группируются
    по совместимому типу ответа, а media insights запрашиваются field expansion вместе с
    публикациями: это сокращает сотни HTTP-вызовов до нескольких десятков и позволяет обработать
    весь портфель в лимите функции. Автопривязка использует только точное совпадение или явный
    alias; неоднозначный аккаунт нельзя назначать клиенту по догадке.
45. **Пауза проекта — единый операционный стоп, а не только сортировка** — скрывать проект ниже
    списка недостаточно: уже созданные задачи продолжали попадать на доску, а активный шаблон
    мог сгенерировать новую работу. Поэтому `paused`/`finished` исключаются из всех оперативных
    выборок; DB-trigger переводит открытые задачи проекта в `paused`, что одновременно закрывает
    автоинтервал времени, и выключает `recurring_tasks`. Генератор повторов дополнительно проверяет
    стадию проекта. При возврате в `launching`/`active` задачи снова видны в колонке «На паузе»,
    а шаблоны включаются только вручную — это защищает от неожиданной автогенерации.
46. **Порядок канбан-карточек вычисляется из бизнес-признаков, а не хранится вручную**
    *(заменено ADR 54)* — доска
    предназначена для выбора следующей работы, поэтому внутри каждой колонки сначала идут
    просроченные и сегодняшние задачи, затем отмеченные срочными и важными, после них уровни
    приоритета и ближайший дедлайн. Ручной порядок карточек не сохраняется: после drag-and-drop
    задача занимает место согласно текущей срочности. «На паузе» стоит перед «На проверке»,
    потому что остановленная работа требует решения до ожидания внешней проверки.
47. **Большой клиентский проект делится на направления, а не на десяток самостоятельных
    проектов** — проект остаётся единицей договора, команды и клиентского отчёта; направление
    представляет продукт, подпроект или рекламную инициативу внутри него. У направления должны
    быть собственные статус, ответственный, задачи, повторы, KPI/бюджет и привязки рекламных
    кампаний, а аналитика должна уметь показывать как весь проект, так и один такой срез.
    Отдельный проект создаётся только при отдельном договоре, бюджете, команде или отчётности.
    Это соответствует компонентам/workstreams в Jira и sections/lists в Asana/ClickUp и не
    создаёт лишнюю вложенность. Текущий `tasks.workstream` сохраняется как совместимое текстовое
    поле до миграции на справочник направлений; глубже уровня «направление → задача → подзадача»
    иерархию не добавляем.
48. **Нулевой расход нельзя показывать без проверки свежести источника** — пустой диапазон после
    истечения Meta-токена визуально неотличим от реального нулевого расхода и ведёт к неверным
    выводам. Поэтому рекламный экран отдельно запрашивает максимальную дату метрик по выбранному
    проекту и предупреждает, если она более чем на сутки отстаёт от конца периода. Секретный
    токен по-прежнему хранится только в Vercel; его состояние не записывается в БД.
49. **Все выполненные задачи удаляются через три дня после завершения** — единственным
    источником срока служит `completed_at`, а не дедлайн. Это правило заменяет прежний архив
    30+30 дней и отдельную двухдневную очистку личных задач. Три дня задача доступна для
    случайного возврата из «Сделано», затем ежедневный `pg_cron` удаляет её вместе с зависимыми
    чек-листами, комментариями и вложениями. История трудозатрат сохраняется отдельно снимком.

50. **Статус работы и человеческий фокус — разные сущности** — `in_progress` показывает
    состояние задачи, но не доказывает, что человек непрерывно занимается ею. Точное время
    хранится в непересекающихся `focus_sessions`, которых у человека одновременно может быть
    только одна; прежние `task_time_entries` остаются грубой исторической оценкой. Ожидание
    нейросети — отдельный статус `ai_wait`, который закрывает человеческий фокус. Лимит трёх
    активных задач остаётся мягким предупреждением, потому что агентство действительно ведёт
    часть работ параллельно.

51. **Медиаплан нормализуется в Agency OS, а Google Sheets служит импортом** — фактические
    метрики уже живут в `ad_*`, поэтому план должен иметь стабильные ключи метрик, период,
    направление и валюту. Ссылка на произвольную таблицу не подходит как runtime-источник:
    владелец может переставить колонки или удалить лист. Импорт сначала валидируется и создаёт
    версионный снимок; утверждённый план не переписывается незаметно. Полная схема описана в
    `docs/MEDIA_PLAN_PROPOSAL.md`. Модель согласована и реализована в 0029–0030: один
    approved-план на проект/направление/период/валюту. Общий план может считать весь проект;
    у плана направления кампания обязательна, чтобы не приписывать ему факт других работ.
    Несколько валют и направлений всегда отображаются отдельными карточками.

52. **Часто меняемые поля задачи редактируются на месте, полная карточка остаётся единой** —
    исполнитель и приоритет нужны при ежедневной сортировке работы, поэтому доступны как
    компактные select-поля в «Дне», «Списке» и канбане. Название задачи открывает общий
    `TaskDrawer` для описания, дат, ссылок и остальных полей. Быстрые select-поля используют
    одну server action с Zod, RLS и возвратом фактически сохранённого значения; отдельные
    несовместимые редакторы для каждого экрана не создаём.

53. **Три дня в «Сделано» считаются календарными датами, а не 72 часами** — пользователю
    важно, чтобы утром третьего следующего дня старая карточка уже исчезла. Операционная дата
    считается в `Asia/Bangkok`, как личное расписание владельца. UI скрывает просроченные
    done-задачи сразу, а ежедневный `pg_cron` физически удаляет их из БД; так расписание cron
    больше не создаёт лишний четвёртый день видимости. Этот срок хранения намеренно не зависит
    от часового пояса отображения личного календаря.

54. **Автоматический и ручной порядок канбана — два явных режима** — автоматическая очередь
    остаётся безопасным режимом по умолчанию: наличие дедлайна и приоритета, срок и уровень
    приоритета определяют следующую работу. Для осознанного планирования пользователь включает
    «Мой порядок» и переставляет карточки внутри/между колонками; `board_position` хранится в БД,
    а режим — в браузере. Порядок целевой колонки записывается одной SECURITY INVOKER RPC,
    чтобы не оставлять частичный результат и не обходить RLS. При обычной смене статуса старая
    позиция сбрасывается, иначе номер из прежней колонки неожиданно влиял бы на новую.

55. **Meta обновляется серверным cron, а дашборд показывает только бизнес-сигналы** — основной
    импорт вынесен в общий server-only сервис и ежедневно запускается Vercel Cron в 03:00 UTC.
    Повторно синхронизируются семь дней для запаздывающей атрибуции; endpoint защищён
    `CRON_SECRET`, запись выполняется через `SUPABASE_SECRET_KEY`. `/api/cron/*` исключён из
    пользовательского session-proxy, иначе Vercel получает редирект на login до проверки секрета;
    собственная Bearer-проверка route остаётся обязательной. Техническая несвежесть и
    падение показов не являются пользовательскими тревогами. Сигнал по эффективности возникает,
    только когда CPA вырос минимум на 20% и число заявок одновременно снизилось; расход без
    результата остаётся отдельным сигналом.

56. **Личный Instagram расширяет существующий проект, а не создаёт дубль** — проект личного
    бренда уже является контейнером задач, повторов и контентной аналитики, поэтому
    `@katerina_pro_digital` остаётся связан с тем же `project_id`, а проект получает понятное
    имя «Катерина Анисимова · Личный Instagram». В агрегате «Все проекты» нет проектного
    логотипа: аватар произвольного первого аккаунта создаёт ложное ощущение выбранного бренда.

57. **Восстановление пароля выполняется только через Supabase Auth recovery-flow** — пароль
    нельзя получить из базы или Git, поскольку Auth хранит только его криптографический хеш.
    Публичная страница запроса отправляет письмо с `redirectTo=/reset-password`, а отдельная
    публичная страница меняет пароль только после получения временной recovery-сессии. Это
    безопаснее администраторских «временных паролей», не требует передавать секрет в чате и
    не открывает остальные маршруты дашборда.

58. **Яндекс.Директ использует общую рекламную модель, а не отдельный модуль** — кабинет
    хранится в `ad_accounts` с `platform = 'yandex_direct'`, а кампании, группы, объявления,
    метрики и цели записываются в существующие `ad_*`. Так внутренний и клиентский отчёты
    сравнивают каналы единообразно, но исходная платформа и валюта всегда сохраняются. Один
    токен специального представителя агентства перечисляет клиентов через `AgencyClients.get`;
    остальные запросы выполняются отдельно для каждого `Client-Login`, чтобы сбой одного
    клиента не останавливал портфель. Неоднозначная привязка кабинета к проекту подтверждается
    вручную, а не угадывается по похожему названию.

59. **Интеграции рекламных площадок Agency OS работают только на чтение** — токены Meta и
    Яндекса предназначены для ingestion и аналитики. Код не меняет ставки, бюджеты, статусы,
    объявления и настройки кампаний. Токены живут только в sensitive env Vercel, не пишутся
    в Git/БД/логи и не передаются клиентскому браузеру. Изменение рекламы остаётся отдельным
    человеческим действием за пределами аналитического sync.

60. **ИИ-анализ строится поверх воспроизводимого снимка и не является автопилотом** — сначала
    детерминированный слой проверяет свежесть, цели, валюты, периоды и рассчитывает метрики;
    только затем модель получает ограниченный JSON и возвращает структурированные выводы с
    доказательствами, уверенностью и недостающими данными. Анализ хранит model/prompt version и
    исходный снимок. Модель не смешивает валюты, не додумывает отсутствующие конверсии, не
    меняет рекламу и не публикует клиенту внутренние рекомендации без просмотра владельцем.
    Провайдер модели выбирается конфигурацией server-side, а не зашивается в доменную модель.

61. **Первичная проверка Яндекс.Директа выполняется вручную и без записи в БД** —
    `AgencyClients.get` вызывается owner-only Server Action без `Client-Login`, поэтому один
    read-only запрос возвращает весь доступный агентскому представителю перечень. Результат
    нужен для ручного сопоставления и не создаёт `ad_accounts`, не запускает backfill и не
    открывает cron. Токен читается только server-side из sensitive `YANDEX_DIRECT_TOKEN`;
    клиент получает лишь нормализованные поля логина, названия, валюты и архивности.

## Пробовали и отказались

- **Локальный E2E без разрешённого сетевого доступа** — базовая песочница блокирует
  `*.supabase.co` и `*.vercel.app`. В сессии 2026-07-19 разрешённый egress использован только для
  целевых Auth/REST и production-проверок; полноценного постоянного E2E-набора пока нет.
- **`isDueToday()` внутри today-sort** — использовала реальную дату вместо параметра `today`,
  тесты упали при смене суток. Заменено на прямое сравнение `due_date === today`.
- **Embed `responsible:profiles(...)` без хинта** — падал PGRST201 (двусмысленность из-за
  project_members). Всегда писать `profiles!projects_responsible_id_fkey`.
- **seed-скрипт с SUPABASE_SERVICE_ROLE_KEY** (scripts/seed.mjs) — оставлен для локалки,
  но прод сидился напрямую SQL-ом через MCP (сервис-ключ в песочницу не передавали).
- **MCP Supabase/Vercel в сессии 2026-07-19 был недоступен** — миграция уже оказалась применена
  предыдущей попыткой и была подтверждена SQL-проверками; внешний деплой выполнен через Vercel
  CLI, а Supabase QA — через авторизованный Dashboard и публичные Auth/REST API.
- **MCP Supabase/Vercel в сессии 2026-07-23 снова не обнаружился** — состояние миграций
  подтверждено в авторизованном SQL Editor, production-деплой выполнен Vercel CLI в тот же
  project/team. При CLI важно запускать из корня репозитория, явно связанного с существующим
  project ID: запуск из `agency-os/` при серверном Root Directory=`agency-os` ищет вложенный
  `agency-os/agency-os`.

## Ограничения, о которых помнить

- MCP-коннекторы (Supabase/Vercel/Notion) в сессиях нестабильны — флапают; критичные SQL
  сохранять во временный файл до применения. Разрешённый fallback должен использовать те же
  project/team ID и обязательно завершаться проверкой production.
- Обсидиан-хранилища у ассистента нет — «память проекта» живёт в repo (CLAUDE.md, docs/*)
  + заметка-дубль отдаётся файлом для ручного переноса в Obsidian.
- Ветка разработки: `claude/agency-ops-mvp-design-ykrrn0`; в main не мержилось, PR нет.
