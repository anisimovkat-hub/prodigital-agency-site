# Яндекс.Директ и ИИ-анализ рекламы

Статус: Y1 access/discovery реализован; ждёт проверки фактического списка и ручной привязки.
Обновлено: 2026-08-20.

## Цель

Agency OS должна автоматически собирать рекламную статистику всех активных проектов из
Яндекс.Директа в тот же раздел «Аналитика», где уже находятся Meta и Instagram, а затем
формировать проверяемые выводы и рекомендации по каждому проекту.

Два обязательных ограничения:

- интеграция работает только на чтение и никогда не меняет ставки, бюджеты, объявления или
  настройки кампаний;
- ИИ не получает права выполнять рекомендации. Он объясняет данные, ссылается на конкретные
  показатели и оставляет решение человеку.

## Что уже есть

- нормализованные таблицы `ad_accounts`, `ad_campaigns`, `ad_sets`, `ads`, суточные метрики,
  конверсии и аудитория;
- единый внутренний экран `/analytics` и публичный read-only отчёт клиента;
- ежедневный защищённый Meta-sync через Vercel Cron;
- раздельный расчёт денежных показателей по валютам и проектам;
- правила бизнес-сигналов: рост CPA учитывается только вместе со снижением заявок; падение
  показов и техническая свежесть не создают пользовательский шум.

Отдельных таблиц и отдельного дашборда только для Яндекса создавать не нужно.
`ad_accounts.platform = 'yandex_direct'` отделяет источник, а общая схема позволяет сравнивать
каналы без дублирования интерфейса.

## Этап Y1 — доступ и перечень клиентов

Ручной шаг владельца выполняется один раз:

1. Проверить OAuth-приложение Яндекса с правом `direct:api`.
2. Получить токен специального представителя агентства, который видит нужных рекламодателей.
3. Сохранить токен только в sensitive env Vercel как `YANDEX_DIRECT_TOKEN` для Production и
   Preview. Не помещать его в Git, Supabase, документацию, клиентский JS или логи.

Сервер вызывает `AgencyClients.get` без заголовка `Client-Login` и получает перечень клиентов
агентства: логин, ClientId, название, валюту и архивный статус. Для всех остальных запросов
конкретного рекламодателя используется тот же OAuth-токен и его `Client-Login`. API Яндекса
обрабатывает одного рекламодателя за запрос, поэтому синхронизация должна изолировать ошибки:
сбой одного клиента не останавливает остальные.

Реализация Y1: `src/lib/yandex-direct.ts` — server-only адаптер, а owner-only блок
`/analytics` запускает его вручную и показывает логин, название, валюту и архивность. Ответ не
пишется в БД, исторические данные не загружаются, `Client-Login` пока не используется.

Официальные источники:

- [AgencyClients](https://yandex.ru/dev/direct/doc/ru/agencyclients/agencyclients)
- [AgencyClients.get](https://yandex.ru/dev/direct/doc/ru/agencyclients/get)
- [Работа агентства с несколькими клиентами](https://yandex.ru/dev/direct/doc/en/best-practice/agency)
- [OAuth и доступ к API](https://yandex.ru/dev/direct/doc/en/concepts/auth-token)
- [Reports service](https://yandex.ru/dev/direct/doc/en/how-to)

## Этап Y2 — безопасная привязка к проектам

- Каждый клиент Яндекса создаётся/обновляется в `ad_accounts` с исходной валютой и
  `platform = 'yandex_direct'`.
- В интерфейсе владелец явно привязывает кабинет к проекту Agency OS. Точное заранее
  подтверждённое соответствие можно сохранить как alias, но неоднозначные названия нельзя
  связывать автоматически.
- Архивные клиенты сохраняются для истории, но не входят в текущую синхронизацию.
- Один проект может иметь несколько кабинетов Meta и Яндекса; один кабинет относится только
  к одному проекту, пока не реализована отдельная привязка кампаний.

Критерий готовности: на служебном экране видны все доступные логины агентства, их валюта,
проект, состояние привязки и результат последней попытки синхронизации.

## Этап Y3 — структура и статистика

Для каждого привязанного активного клиента:

1. Загрузить кампании, группы и объявления через API v5 и upsert в существующие таблицы.
2. Через Reports получить суточные расход, показы, клики и конверсии по целям.
3. Хранить каждую цель отдельно, например `yandex_goal:<goal_id>`, с читаемым названием.
4. Не складывать деньги разных валют. Валюта кабинета остаётся источником истины.
5. Обрабатывать ответы Reports `201/202` повторной проверкой с задержкой, а ограничения API —
   контролируемым backoff без бесконечных повторов.
6. Первый импорт выполняет ограниченный backfill, последующие — скользящие семь дней для
   запаздывающей атрибуции.

Критерий готовности: для каждого связанного проекта суммы и конверсии за контрольный период
совпадают с интерфейсом Яндекс.Директа; дерево кампания → группа → объявление раскрывается в
«Аналитике», а источник можно выбрать фильтром Meta / Яндекс / все каналы.

## Этап Y4 — автоматическая загрузка

- Добавить защищённый server-only endpoint `/api/cron/yandex-sync` и расписание Vercel Cron.
- Использовать `CRON_SECRET` и server-side Supabase key; пользовательская сессия не требуется.
- Синхронизировать только кабинеты активных проектов, но сохранять исторические метрики.
- Хранить технический результат каждой попытки: время, клиент, диапазон, число строк и краткую
  безопасную ошибку без токена.
- Не показывать технические ошибки на главном дашборде. Они доступны владельцу в состоянии
  источников; рабочий сигнал создаётся только из надёжных бизнес-метрик.

## Этап A1 — доказательный слой для ИИ

ИИ нельзя подключать прямо к сырым строкам. Сначала сервер строит детерминированный снимок:

- проект, канал, кабинет, период и свежесть источника;
- расход, заявки/целевые действия, CPA/CPL, клики, CTR и динамика относительно прошлого периода;
- результаты по кампаниям, группам, объявлениям и целям;
- план/факт медиаплана, если план настроен;
- валюта каждой денежной метрики;
- конфигурация проекта: основная цель, допустимый CPA/CPL и вторичные цели.

Если данные несвежие, цель не выбрана или периоды несопоставимы, снимок явно сообщает
«недостаточно данных». ИИ не должен додумывать нулевые значения или смешивать валюты.

## Этап A2 — формат ИИ-анализа

Модель получает только подготовленный снимок и возвращает JSON по фиксированной схеме:

- `summary` — 2–4 предложения о результате периода;
- `findings[]` — наблюдение, серьёзность, конкретные доказательства и уверенность;
- `recommendations[]` — рекомендуемое действие, ожидаемый эффект, риск и что проверить;
- `missing_data[]` — чего не хватает для уверенного вывода.

Каждый вывод обязан ссылаться на конкретную метрику, период и объект рекламы. Общие фразы без
доказательств не показываются. Рекомендации не выполняются автоматически и не отправляются
клиенту без просмотра владельцем.

Сохраняется версия анализа: проект, период, источники, timestamp данных, модель, версия
промпта, входной снимок и ответ. Это позволяет воспроизвести вывод и отличить изменение
данных от изменения модели.

## Этап A3 — интерфейс

- Внутри проекта: короткое резюме, 3–5 главных наблюдений и конкретные рекомендации.
- На портфельном экране: только проекты, где одновременно ухудшились цена и количество
  целевых результатов либо появился расход без результатов.
- Сначала запуск «Проанализировать» вручную для контроля стоимости и качества.
- После проверки на нескольких проектах — ежедневный или еженедельный фоновый анализ только
  при появлении новых данных.
- Публичный отчёт клиента получает отдельное простое резюме после внутреннего подтверждения;
  технические ошибки и внутренние рекомендации туда не попадают.

## Порядок реализации

1. Y1: проверить доступ агентского токена и получить полный перечень клиентов.
2. Y2: сделать экран явной привязки кабинетов ко всем активным проектам.
3. Y3: импорт структуры и метрик, сверка минимум трёх разных проектов.
4. Y4: ежедневный cron и наблюдаемость источников.
5. A1: проектные KPI и воспроизводимый аналитический снимок.
6. A2: server-only интеграция модели и строгий JSON-ответ.
7. A3: внутренний интерфейс, QA на реальных данных, затем безопасная клиентская версия.

До завершения Y3 ИИ-анализ рекламных кампаний не считается готовым: красивые рекомендации
на неполных данных опаснее отсутствия рекомендаций.
